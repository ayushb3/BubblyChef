### The #315 → #322 chain, because it explains the shape of the code now

`ingredients` is a JSONB column that legitimately holds **two shapes**: `Ingredient`
objects (AI generation, URL import) and plain strings (`RecipeEditModal`, which
flattened them on save). The detail page read only the object shape, so string rows
labelled as `''` and rendered blank — correct count, no error, looked like CSS.

#315 fixed the reader by putting the dual-shape rule in one place
(`ingredientParts`/`ingredientLabel` in `lib/recipe-helpers.ts`). #322 fixed the
*writer* that was creating the string shape in the first place. Both are merged, so
`lib/recipe-helpers.ts` is now the single home for ingredient-shape handling — new
readers should call it rather than hand-rolling `typeof ing === 'string'`.

**The cook flow was never affected** — `cook_matcher.py` has always guarded both
entry points with `isinstance(ingredient, str)`. Worth knowing before anyone
re-investigates.

### #328 — what a reviewer should know

Backend only; **no UI change lands**. Linked as `Related to`, not `Fixes`, because the
user-visible bug is intact until the frontend follows.

The load-bearing decision: **the LLM writes the copy but does not pick the recipe.**
Selection is deterministic and unit-testable. This is not stylistic — an LLM asked to
choose could name a recipe the user hasn't saved, producing a broken deep link, which
is the exact defect #306 just fixed. Rather than instructing the model not to pick,
`DashboardCopyResult` **has no recipe field at all**, so a pick is structurally
inexpressible.

Four blockers were found in review, none of which the 546 passing tests caught:

1. Meal buckets computed in **UTC for every user** — an LA user at 19:00 local ranked
   against `snack`, while the greeting reads the browser's clock. #306's complaint,
   recreated server-side. Route now takes `tz_offset_minutes`.
2. The bucket rule was hand-rolled from the **greeting's** boundaries — and the design
   doc said to do that. Wrong: #306's lesson was about *wording*, but ranking *matches*
   against a stored `meal_type` tag, so it must use the rule that produced the tag. The
   two disagreed **7 hours in 24**. `domain/mealtime.py` is now one shared rule.
3. **The tip wasn't pantry-grounded** — two users with different pantries got
   byte-identical prompts. That is the whole of #225.
4. The cache kept serving **"Chicken soup" to a pantry with no chicken** — revision was
   `max(updated_at)`, which doesn't move when a non-newest row is deleted.

## Auth audit — three issues filed, none fixed

Asked to look at the login flow. Findings, in the order I'd spend attention:

### #330 — sign-up appears to fail silently *(highest value)*

`login/page.tsx:26-41` checks only `error` from `signUp`, never whether a **session**
came back. With email confirmation enabled (Supabase's default), `signUp` succeeds with
`session: null`, the code pushes to `/`, middleware sees no user, and bounces straight
back to `/login` — **no error, no "check your email"**. The user assumes it failed and
retries; the second attempt errors with "User already registered", which makes it look
broken rather than nearly-successful.

**Unverified.** There is no `nextjs/.env.local` in the container, so I could not run
against a real Supabase project to confirm whether confirmation is actually on. **First
step for whoever picks this up is checking that setting** — if it's off, this drops from
a first-run blocker to a robustness fix.

Profile creation is *not* a problem: `migrations/00002_rls_policies.sql:87-104` has an
`on_auth_user_created` trigger that inserts the `user_profiles` row correctly.

### #331 — there is no sign-out

`grep -rn "signOut\|logout\|sign out" nextjs/src` → **zero matches**. No nav item, no
profile action, nothing. Once signed in you stay signed in until the session expires or
cookies are cleared.

Beyond the obvious shared-device problem, this **blocks manual verification of anything
per-user** — including #225's per-user tips — because you can't switch accounts without
clearing storage.

### #332 — the app is a hard login wall *(product decision, not a bug)*

`publicPaths` is exactly `['/login', '/auth/callback']`. No landing page, no demo, no
guest mode: a visitor cannot see anything the app does before creating an account.
Filed so it's a deliberate choice rather than a side effect of blanket route protection.
