The shape of the system

One browser, two backends, one database.

BubblyChef looks, from the browser, like a single app. It isn't one. Every request the browser makes goes to one of two independently deployed programs, written in two different languages, running on two different hosts — and both of them read and write the same Postgres database, through two different doors.

Two rules keep this legible instead of turning into spaghetti, and they're stated plainly in this repo's own CLAUDE.md: the two API surfaces are never mixed — CRUD always goes through Next.js, AI operations always go direct to the microservice — and every AI call goes through one abstraction, so nothing in the app talks to the Gemini SDK directly. Both rules exist for the same reason: a split system only stays sane if each side has exactly one job.

Why split at all

The two halves of this app want different things from their runtime.

The instinct when you're building alone is to keep everything in one process — one language, one deploy, one thing to reason about. BubblyChef resists that on purpose, because the two things it does don't behave alike:

CRUD

Shape of a request
Short. Read a row, write a row, return JSON. Milliseconds.
What it needs
Nothing exotic — a database client and a router. TypeScript is fine; it's the same language as the UI calling it.
How it scales
Trivially — stateless functions, spin up on demand, spin down to zero.

AI orchestration

Shape of a request
Long, and often staged — classify intent, fetch context, call a model, maybe call it again. Seconds, and streamed.
What it needs
LangGraph, LangChain, the Gemini/Ollama SDKs — an ecosystem that lives in Python, not the frontend's TypeScript.
How it scales
By a completely different cost curve — model calls dominate, not request count.

That's the actual principle, and it's worth separating from the specific technologies: split by workload shape, not by what resource is being touched. "Pantry stuff" and "recipe stuff" both touch the same tables, but they aren't split from each other — /api/pantry and /api/recipes are neighbors in the same Next.js app. What's split is short synchronous CRUD from long, multi-step, model-calling orchestration — because those two things want different runtimes, not because they touch different nouns.

The app layer

Next.js on Vercel — same-origin CRUD, nothing clever.

Every pantry read, every recipe save, every profile edit goes through a Next.js route handler under app/api/. The job here is deliberately boring: authenticate the request, touch exactly the rows this user owns, return JSON. Here's the actual gate every route passes through first:

nextjs/src/lib/response-helpers.ts
export async function requireAuth(): Promise<
  [SupabaseClient, User] | NextResponse
> {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()

  if (!user) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }
  return [supabase, user]
}

Notice what this function doesn't do: it doesn't decide what the user is allowed to touch. It just answers "who is this?" and hands back a Supabase client already carrying that identity. The actual row-level permission check happens one layer down, at the database — more on that in a moment, because it's the most important idea in this whole document.

Why Next.js for this half specifically, rather than any other backend framework? Because the CRUD layer and the UI are the same audience and the same language. A route handler and the component that calls it live in the same repo, the same type system, often the same file's neighborhood — there's no schema to keep in sync across a network boundary for something as simple as "save this recipe." Same-origin also means no CORS configuration, no separate auth token dance for the common case: the browser's session cookie is the credential.

The reasoning layer

FastAPI + LangGraph on Railway — multi-step, model-calling, streamed.

Ask BubblyChef's chat "what can I cook tonight," and a lot happens before you see a word: classify what you're asking for, fetch your pantry, extract constraints (cuisine, time, diet) with one model call, deterministically rank recipe candidates by expiry urgency, then generate a grounded response with a second model call. That's not one function — it's a graph:

classify_intent → [recipe-generate]
  ↓
gather_pantry_context       # fetch items + expiring
  ↓
extract_constraints         # LLM → structured RecipeConstraints
  ↓
score_and_rank               # deterministic: expiry urgency + fit
  ↓
generate_grounded_response  # LLM, with structured context — not a raw pantry dump

LangGraph is what makes this a graph instead of one enormous prompt. Each node is a small, independently testable Python function with typed state in and typed state out — the ranking step is plain deterministic code, not the model's opinion, which is exactly why expiry-vs-coherence bugs in this app show up as a scoring-weight problem you can unit test, not a prompt-wording problem you can only eyeball. This is the shape LangGraph is built for, and it's a Python-ecosystem tool — which is most of why this half of the app isn't TypeScript.

The other reason is the proposal pattern, stated as a rule in this repo's own conventions: nothing writes to the database without user confirmation. Every workflow here returns a proposal with a confidence score, not a committed write — high confidence auto-suggests, medium asks for review, low gets dropped. That's a deliberate seam between "the model decided something" and "the database changed," and it's one more reason this logic doesn't live inline in a CRUD route: it's a genuinely different kind of function, one that reasons about uncertainty instead of just moving rows.

One abstraction, two providers

Nothing in this layer calls the Gemini SDK directly. Every model call goes through an AIManager that tries providers in order — Gemini first, Ollama as a local fallback — so a provider outage degrades the app instead of breaking it, and swapping models (as this project did, moving to gemini-3.1-flash-lite) is a one-line config change, not a rewrite.

Supabase — the substrate both services stand on

One managed Postgres, one identity provider, two very different trust levels.

This is the part that actually makes the two-service split affordable. If BubblyChef had to hand-roll a database, an auth system, and a way for two separate backends to agree on "who is this user," the split above would cost far more than it's worth. Supabase collapses all three into one thing both services can point at.

The database enforces what the app might forget

Every table's permission rule looks like this — plain SQL, not application code:

supabase/migrations/00002_rls_policies.sql
ALTER TABLE pantry_items ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users manage own pantry items"
  ON pantry_items FOR ALL
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

That policy runs inside Postgres, on every query, regardless of which service sent it or whether that service's code remembered to add a WHERE user_id = ? clause. This is the core idea worth carrying into any system: push the invariant that matters most into the layer that can't be skipped. Application code has bugs, forgets things, gets refactored by someone in a hurry. A database constraint, checked on every single query, doesn't have an "oops, forgot that route" failure mode.

But this backstop only exists for the path that uses it — which is exactly where the two services stop being symmetric.

Two keys, two trust models

Next.jsai-service
NEXT_PUBLIC_SUPABASE_ANON_KEY, scoped by the user's own session BUBBLY_SUPABASE_SECRET_KEY — Supabase's service_role key
Row-Level Security applies. A query for someone else's pantry returns nothing, full stop, enforced by Postgres. Row-Level Security is bypassed entirely by design — this key can read or write any row.
Correctness is guaranteed twice: once by the route handler's logic, once by the database underneath it. Correctness is guaranteed exactly once — by the code. Which is why every repository method's first parameter is user_id, filtered by hand: 
async def get_all_pantry_items(self, user_id: str) -> list[PantryItem]:
    ...

That's not a style choice — it's the entire safety net for this half of the app, spelled out as a function signature convention because there's no database-level one to lean on. The service_role key exists because the AI service genuinely needs it: it has to read across whatever the workflow needs, act on the user's behalf inside a multi-step graph, and RLS's per-request model doesn't compose cleanly with that. The trade is real, not a mistake — you get power, in exchange for the app being the only thing keeping user boundaries straight.

One identity, verified twice, never shared

Supabase Auth issues a single signed JWT when you log in. The interesting part is what happens next: the two services never talk to each other to agree on who you are. There's no shared session store, no internal "am I really logged in" round-trip between Next.js and ai-service. Each one verifies the same token independently, against the same source of truth:

ai-service/bubbly_chef/api/auth.py
def _decode_with_jwks(token: str) -> dict[str, Any]:
    """Decode JWT using Supabase JWKS (ES256)."""
    client = _get_jwks_client()
    signing_key = client.get_signing_key_from_jwt(token)
    return jwt.decode(
        token, signing_key.key,
        algorithms=["ES256"], audience="authenticated",
    )

Next.js verifies the same JWT its own way — via the supabase-js client's session handling. Both arrive at the same answer, independently, because both trust the same issuer rather than trusting each other. This is the pattern worth remembering: stateless, signed tokens let you add a third, fourth, fifth service later without ever touching a shared session table. That's a large part of what "the power of Supabase" cashes out to in practice — not a specific feature, but that identity becomes a fact both services can check for themselves, instead of infrastructure you'd otherwise have to build and keep in sync by hand.

Why Vercel and Railway, specifically

Matching the host to what the runtime actually needs, not just "a place to deploy."

Vercel is built by the same team as Next.js, and it shows in exactly the ways that matter for the CRUD layer: push a branch, get a full preview deployment at a real URL — which is what's actually posting that "Ready — Preview" comment on every pull request in this repo. Serverless functions that scale to zero between requests fit a workload made of thousands of short, independent reads and writes. There's no server to patch, size, or leave idling overnight for three users.

Railway earns its keep on the opposite property: it's fine with a process that stays up, holds a connection open, and streams. The ai-service's chat endpoint is server-sent events — tokens arriving as the model produces them, not a request that returns once and disappears. A model call can also legitimately take several seconds across a multi-node LangGraph run; a platform built around short serverless function timeouts fights that shape, a platform built around long-running containers doesn't.

Neither choice is about one platform being "better." It's the same principle as the service split itself, one level down the stack: a short, stateless, bursty workload and a long, stateful, streaming one want different hosts, for the same reason they wanted different frameworks.

The cost of the split — a real bug

Splitting a system means splitting the places its rules can live.

None of the above is free, and the honest version of this document says where it actually bit. Issue #182 added estimated_expiry — a flag meaning "this date was guessed, not confirmed" — with a matching rule: if a user later corrects the date by hand, the guess-flag must clear. One invariant, plain to state.

The trouble is that a pantry item's expiry date can be written from either service — the ai-service, when it estimates a date during receipt scanning, and the Next.js CRUD route, when a person edits the item by hand in the pantry UI. The fix landed in the ai-service's write path:

ai-service/bubbly_chef/repository/supabase_repo.py
# clear the estimated_expiry flag unless the caller explicitly set it
if "expiry_date" in updates and "estimated_expiry" not in updates:
    updates["estimated_expiry"] = False

It did not land in the Next.js route. PUT /api/pantry/[id] happily updated expiry_date and never touched estimated_expiry at all — because it's a different file, in a different language, reviewed as a different piece of work, and nothing forced the two to be checked together. It shipped clean: types checked, tests passed, CI was green. The badge just kept reading "(est.)" on a date a person had just told the app was correct, and nobody knew until someone opened the real app in a real browser and manually corrected a date — the one kind of check a split system with independently green CI on both sides doesn't get for free.

The general shape of this failure

It isn't really an auth story or a language story — it's what happens whenever one invariant has more than one place it can be written from. Two services, two write paths, and a monolith with two code paths for the same reason all have this exact failure mode. Splitting into services doesn't create the risk; it just makes each write path further apart, in a different language, on a different reviewer's desk, with its own green CI — so the two are much less likely to be looked at side by side.

The fix isn't "don't split services." It's to know, for each invariant, whether it has one writer or several — and if several, either centralize the write (one function every path calls through) or write a test that exercises the invariant from every path that can touch it, not just the one you happened to be working in.

What transfers to other systems

None of this is BubblyChef-specific. These are the same five decisions on any stack.

  1. 1
    Split by workload shape, not by resource. Short/stateless vs. long/streaming is a real fork in what a runtime needs. "Pantry vs. recipes" isn't — that's just two endpoints in the same app.
  2. 2
    Push the invariant that matters most into the layer that can't be skipped. A database constraint checked on every query beats an application check that a future refactor might forget to include.
  3. 3
    Bypassing that layer is sometimes the right call — but know you did it. The service_role key is a legitimate trade for the power a multi-step AI workflow needs. The cost is that correctness moves entirely into code, and someone should be able to name where.
  4. 4
    One signed identity, verified independently, beats a shared session store. It's what lets two services — or five, later — agree on "who is this" without ever having to talk to each other about it.
  5. 5
    A split write path is a promise to keep two implementations of the same rule in sync. Budget for that explicitly — either one function every path routes through, or a test that walks every path, not just the one in front of you.
